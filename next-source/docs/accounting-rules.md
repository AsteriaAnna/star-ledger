# G1 账务规则与验收范围

日期：2026-09-28；代码版本：0.3.0。测试共 76 项（G0 25、G1 31、状态/补认 20）。

## 输入与输出

所有金额使用 CNY 整数分；账户类型是 ASSET/LIABILITY。资产 Movement 正数增加余额，负债 Movement 正数增加欠款。负债还款与退款生成负数 Movement。浮点数、无效日历日期、空名称、同账户内部转账在写入前拒绝。

业务层创建一个 Transaction，按实际语义创建零到多条 BalanceMovement、ConsumptionEffect 与关联。它们与 Operation/Outbox 在同一次 SQLite 事务中提交，同一 Command 在同一个 Batch 中同步。余额和消费查询都是纯计算。

| 场景 | 余额变化 | 消费影响 |
|---|---|---|
| 银行卡消费 44 元 | 银行卡 -44 | +44 |
| 零钱消费 44 元 | 零钱 -44 | +44 |
| 母亲提供的亲情卡消费 44 元 | 无本人余额变化 | +44 |
| 付款账户暂未知 | 保存 unresolved movement | 正常计消费 |
| 消费退款 30 元 | 退款到账账户 +30；若信用账户则欠款 -30 | -30 |
| 内部充值 100 元 | 转出 -100、转入 +100 | 0 |
| 提现本金 1500、手续费 1.50 | 转出 -1501.50、转入 +1500 | +1.50 |
| 外部转账 100 元 | 付款账户 -100 | 默认 0，可明确补消费语义 |
| 押金 100、退回 80 | 付款 -100、退回 +80 | 0；未退 20 不擅自判断为消费 |

## 本轮明确的统计口径

1. **跨月退款按退款发生时间冲减。** 9 月消费 100、10 月退回 30：9 月 100，10 月 -30。可追溯链接保留原交易。暂不实现“回溯修改原消费月”的第二套分析口径。
2. **期初余额是一个时点的余额。** 仅累加 occurred_at 严格晚于 opening_balance_at 的 Movement。该时点及更早的补导流水仍保留消费统计，但不重复加到余额。用户录入期初余额的 UI 需要说明这一点。
3. **未初始化余额显示未知。** 不把系统内部占位的 opening_balance=0 当作真实余额。
4. **未知账户与外部代付是不同事实。** 未知账户保留待识别 Movement；外部代付不生成属于用户的 Movement。未知账户可用 BIND_ACCOUNT 补认，信用账户会同时换算金额方向。
5. **混合语义的退款不靠比例猜测。** 转账 100，其中 30 计消费，退回 20 时必须明确其中多少冲减消费；否则拒绝自动解释。
6. **有冲突时不输出误导性总额。** 当前查询保守地阻断全部合计，未来 UI 可以进一步区分已确认金额与受影响金额。

以上第 1、2、5 点是本轮为保证可执行而明确的工程口径，尚无 UI，不会自动修改用户真实账本。

## 退款与删除保护

- 本地连续退款不能超过原交易，也不能超过原消费/非消费部分各自的额度。
- 跨端同时新增退款后重新检查合计，超额会生成 `$accounting` 冲突，而不是静默采用一端结果。
- 删除原交易与另一端新建退款也生成冲突；已知存在有效退款时，业务删除入口拒绝直接删除原交易。
- 删除错误退款保留 tombstone，并重新推导原交易可退款额度；同步后可解除相应财务冲突。
- 修改已有退回的转账消费语义需要重新分配冲减额度，本轮拒绝简单改写，等待专门的关联修正命令。

## 边界

所有场景是脱敏结构化测试，尚未做截图/Excel 解析，不宣称真实原始数据识别已经正确。底层通用命令属于内部 API，不可直接暴露给 UI；页面应使用 BusinessAccountingService。

本轮没有自动强去重、Alias、终态纠错、通用金额纠错、外币、分类字典与账户管理 UI。未与真实 GitHub 连接；没有测试 APK、EXE 或跨平台 SQLite 插件。

继承 G0 的实现限制：全历史重放、全量 Fake 拉取、未执行 tsc 静态检查，尚无性能或真实断电保证。账务规则测试通过，不等于允许装载长期真实账本。
