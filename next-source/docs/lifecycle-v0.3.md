# 状态转换、账户补认与迁移 · v0.3

本轮交付 20 项新增测试，总计 76 项通过。没有增加页面、OCR、真实 GitHub 或原生安装包。

## 状态转换

`SET_STATUS` 支持 PENDING → SUCCESS、PENDING → FAILED。已知终态不自动反转，终态修正需后续专用纠错命令。相同状态重复通知为幂等操作；若提供成功确认详情，则检查交易 ID、事件类型、金额、发生时间和已记录的整笔账解释是否一致。

确认成功必须提供完整 settlement，由现有业务解释器重新校验。金额、事件类型和 occurred_at 不能顺便修改；后续若需把下单时间改为支付时间，应先制定明确的时间字段语义。确认保留原交易 ID、用户备注和全部来源记录，新增证据使用新的 SourceRecord ID。

余额变化、消费影响、状态与操作日志在同事务中保存。失败时完整回滚。退款从待处理转成功时重新核对原交易剩余额度，不预占退款金额。

两端相同确认使用稳定的子实体 ID，因果并发的相同创建合并为一个有效实体，不重复计账；不同的整笔账方案用 posting_plan 冲突标识。不同状态也保留所有候选，查询不会绕过冲突计算总额。

posting_plan 保存确认时的结构化解释，仅用于比较，不替代 BalanceMovement/ConsumptionEffect。它不会随后跟着分类修改或账户补认重写。它不包含 SourceRecord 原始 payload。

## 账户补认

`BIND_ACCOUNT` 只用于未知 account_id 的 BalanceMovement；不能借此把已绑定账户改到另一账户。相同补认可重复调用。

账户 ID 与 amount 必须同命令写入。资产按收款为正、付款为负；负债按欠款增加为正，所以未知付款补认为信用账户时方向反转。消费统计及原始证据不变。

内部转账/提现不能补认为负债账户，也不能把两端补认为同一账户。跨端分别补认两个未知端，合并后若落到同一账户，会产生财务约束冲突。

两端同一 Movement 补认到不同账户时，`RESOLVE_ACCOUNT_BINDING` 可显式选择账户并同步更正金额方向。它不会分别处理账户和金额，防止出现不匹配的组合。

## 数据升级

新增 migration_002：transactions.posting_plan，旧记录默认 NULL。v1 数据、操作日志及 outbox 保留。迁移测试建立 v1 的事实与日志，升级后继续确认成功；未使用清库重建。

新客户端接受旧操作中缺失 posting_plan 的创建记录。旧客户端不理解该字段，**所有参与同步的设备需同时升级到 v0.3**；正式协议版本协商留待 G2。当前仍为开发原型，不自动连接任何真实远程仓库。

## 仍需完成
