# v0.5 整笔账冲突解决

新增 RESOLVE_SETTLEMENT 业务命令与 settlementConflictIds 查询函数。输入包含 transactionId、目标 SUCCESS/FAILED、成功时的完整 settlement，以及界面所看到的 expectedOperationIds。

处理流程：检查冲突仍与用户所看到的一致，使用既有账务解释器重新校验完整方案，同事务修改状态、整笔账解释及相关余额/消费影响，生成可同步的解决操作。被否定的余额/消费记录金额置零，实体及历史操作仍保留；零额待识别记录不出现在未知账户列表。

原始 SourceRecord 与用户备注不被覆盖。失败处理不能让已有退款失去有效原交易；财务约束不满足则整笔回滚。多个客户端同时选择不同解决方案，会再次产生冲突。解决操作与删除并发，也会保留生命周期冲突。

新增 9 项测试，总计 104 项通过：成功/失败选成功、不同账户选信用账户、本人付款改为外部代付及后续退款、选择失败、过期选择拒绝、outbox 失败回滚、并发不同解决方案、备注保留、解决与删除并发。

## 边界

本轮提供业务 API，尚无冲突处理页面。不是通用终态纠错工具；必须先存在 status/posting_plan 冲突。它不能自动处理生命周期冲突、任意金额/发生时间更改、来源去重或密钥恢复。

schema 仍为 v3。新的解决语义要求使用 v0.5 客户端一致处理；旧版客户端尚无版本协商阻止机制，正式发行前仍需补上。原生 Android 与可信远端恢复头仍未验证，不能将一次成功同步解释为全部 G2 验收完成。
